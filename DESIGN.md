# Minimi design

Minimi is a single-tool research agent: its only external action is web search. The architecture deliberately separates **memory**, **planning**, **retrieval**, and **answering** so that a question such as “is what I asked last Tuesday still correct?” can be handled as two facts: what the user asked then (durable local record) and what is true now (live evidence).

`POST /api/chat` validates and rate-limits a request, assigns a conversation ID, and opens an SSE stream. The agent writes the user message before reasoning. Its context manager loads the most recent conversation window with UTC timestamps; the planner sees that record plus today’s date and returns compact JSON saying whether live verification is needed and which (at most three) queries would best answer it. Relative dates are explicitly resolved in the planner prompt. Queries run concurrently through Tavily, which returns URLs, snippets, publication dates, and scores. The final GPT OSS prompt receives the conversation record and bounded, labelled evidence only. It must cite source indices and is instructed to say when evidence is unavailable or dated. The answer and exact retrieved source set are then persisted together in SQLite. This makes old answers auditable and lets future turns compare old context with a fresh search.

The model is GPT OSS 120B on Groq: quick enough for an interactive two-pass loop and accessible through a small OpenAI-compatible `fetch` client. Tavily is the sole live-search integration because it gives compact search extracts and publication metadata without adding browsing tools. SQLite is intentionally local, transactional, and zero-ops for a take-home; WAL mode allows responsive reads during writes. The UI is intentionally restrained—white/black/orange—and includes the architecture diagram because the evaluation emphasizes system design. SSE emits planning/search status immediately and answer text in chunks, keeping the transport contract streamable if the provider is later switched to native token streaming.

I rejected a generic autonomous multi-tool framework: it obscures the exact capability boundary, makes tool loops harder to reason about, and is unnecessary with one tool. I also rejected embedding-only memory: for a short personal chat history, timestamped ordered transcript retrieval is more faithful for “what did I ask on a date?” questions. The bounded history and evidence sizes prevent prompt growth.

With another week I would add native Groq streaming, structured claim-to-source validation, search-result caching keyed by query/date, hybrid semantic retrieval once histories grow, a background eval suite for temporal questions, and per-user durable rate limits/authentication. I would also add source page fetching only after measuring whether snippets materially limit answer quality; it is intentionally absent today to preserve the one-tool contract.
